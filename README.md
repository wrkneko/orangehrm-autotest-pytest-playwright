# OrangeHRM Test Automation Framework

End-to-end UI + API automation framework for the [OrangeHRM public demo](https://opensource-demo.orangehrmlive.com),
built with **Python + Playwright + pytest**.

## Structure

- **Page Object layer (`src/pages`)** — one class per page, all Playwright
  interaction lives here. Tests never touch a locator directly.
- **API layer (`src/api`)** — reuses the app's own session to call internal
  endpoints for fast test-data setup/teardown, avoiding slow UI-only flows.
- **Data layer (`src/data`)** — Faker-based factories generate unique data
  per run. This matters because the demo instance is **public and shared**:
  hardcoded names would collide with other people's test runs.
- **Fixtures (`tests/conftest.py`)** — a session-scoped login generates a
  `storage_state` once; per-test contexts reuse it, so tests start on an
  authenticated dashboard instead of repeating the login UI every time.
- **Markers** (`smoke`, `regression`, `ui`, `api`) — let CI run a fast smoke
  suite on every push and a full regression nightly.

```
config/report/
    report.css        # theme for the pytest-html report
    index.css         # theme for the published index page
    build_index.py    # scans the Pages branch, writes index.html
.github/workflows/
    ui-tests.yml      # smoke on push, regression nightly, publishes reports
```

## Setup

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
playwright install chromium

cp .env.example .env             # adjust if needed
```

### Configuration

Everything the framework needs comes from the environment, so the same code
runs locally from `.env` and in CI from repository secrets.

| Variable | Meaning | Default |
| --- | --- | --- |
| `BASE_URL` | Instance under test | `https://opensource-demo.orangehrmlive.com` |
| `ORANGEHRM_USER` | Login for the session-scoped fixture | `Admin` |
| `ORANGEHRM_PASSWORD` | Password for that login | — |
| `HEADLESS` | Run the browser headless | `true` |
| `SLOWMO` | Delay between actions, ms | `0` |

## Running tests

```bash
pytest                           # everything
pytest -m smoke                  # fast critical-path checks
pytest -m regression             # full regression suite
pytest -m api                    # API tests only
pytest tests/ui/test_login.py -v
pytest --headed --slowmo=300     # watch it run
```

Failure artifacts (trace, screenshot, video) are saved under `test-results/`
automatically — open a trace with:

```bash
playwright show-trace test-results/<test-name>/trace.zip
```

## Reporting

Two report formats are produced from the same run.

**pytest-html** — a single self-contained file, themed by `config/report/report.css`:

```bash
pytest -m smoke \
  --html=report/index.html --self-contained-html \
  --css=config/report/report.css
```

**Allure** — steps, attachments and cross-run trends. Results are written to
`allure-results/`; to view a local report:

```bash
pip install allure-pytest
allure serve allure-results
```

### The published index

`config/report/build_index.py` scans the Pages branch and writes a single
`index.html` linking every published run:

```
gh-pages/reports/<suite>/<label>/    pytest-html, one self-contained file
gh-pages/allure/<suite>/<label>/     Allure, generated by the Allure CLI
```

`<suite>` is `smoke` or `regression`; `<label>` is `2026-08-02_17-54-run38`,
i.e. UTC timestamp plus the workflow run number. Labels start with an ISO
date, so sorting them as strings sorts them chronologically — that is the
whole ordering mechanism, there is no state file. Each run directory also
holds a `status.txt` containing `success` or `failure`, which is what colours
the tiles on the index. The formats sit behind a tab switcher; a format with
no runs gets no tab.

Rebuild the page by hand at any time:

```bash
python config/report/build_index.py --pages-dir gh-pages
```

The scan is stateless, so whichever workflow publishes last simply rebuilds
the whole page from what is on the branch.

## Continuous integration

CI lives in a single workflow, `.github/workflows/ui-tests.yml`:

- **push to `main`** → the `smoke` suite;
- **nightly (02:00 UTC)** → the full `regression` suite;
- **manual run** → pick the suite from a dropdown.

Every run publishes both report formats to the `gh-pages` branch and rebuilds
the index.

### One-time repository setup

1. **Create the Pages branch.** The workflow below creates it on first run if
   it is missing, so there is nothing to do here unless you prefer to seed it
   yourself.
2. **Enable Pages.** *Settings → Pages → Build and deployment → Deploy from a
   branch*, branch `gh-pages`, folder `/ (root)`. The index will be served at
   `https://<owner>.github.io/<repo>/`.
3. **Allow the workflow to push.** *Settings → Actions → General → Workflow
   permissions* → **Read and write permissions**. The `permissions:` block in
   the workflow narrows this back down to `contents: write`.
4. **Add credentials.** *Settings → Secrets and variables → Actions*:
   - secret `ORANGEHRM_PASSWORD`
   - variables `BASE_URL`, `ORANGEHRM_USER` (variables, not secrets — masking
     the base URL only makes logs unreadable)
5. **Check `requirements.txt`** contains `pytest-html` and `allure-pytest`;
   the workflow installs nothing beyond it plus the Allure CLI.

### The workflow

```yaml
name: UI Tests

on:
  push:
    branches: [main]
  schedule:
    - cron: "0 2 * * *"          # nightly regression
  workflow_dispatch:
    inputs:
      suite:
        description: Which suite to run
        type: choice
        options: [smoke, regression]
        default: smoke

# Publishing is a push to a shared branch, so runs must not overlap.
# Queue them instead of cancelling — a cancelled run publishes nothing.
concurrency:
  group: ui-tests-pages
  cancel-in-progress: false

permissions:
  contents: write

jobs:
  test:
    runs-on: ubuntu-latest
    env:
      SUITE: ${{ inputs.suite || (github.event_name == 'schedule' && 'regression' || 'smoke') }}
      BASE_URL: ${{ vars.BASE_URL }}
      ORANGEHRM_USER: ${{ vars.ORANGEHRM_USER }}
      ORANGEHRM_PASSWORD: ${{ secrets.ORANGEHRM_PASSWORD }}

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip

      - run: pip install -r requirements.txt

      # Cache the browser, keyed on the Playwright version so a bump in
      # requirements.txt re-downloads a matching build.
      - id: pw
        run: echo "version=$(pip show playwright | awk '/^Version:/{print $2}')" >> "$GITHUB_OUTPUT"

      - uses: actions/cache@v4
        id: pw-cache
        with:
          path: ~/.cache/ms-playwright
          key: playwright-${{ runner.os }}-${{ steps.pw.outputs.version }}

      - if: steps.pw-cache.outputs.cache-hit != 'true'
        run: playwright install --with-deps chromium

      - if: steps.pw-cache.outputs.cache-hit == 'true'
        run: playwright install-deps chromium   # system libs are not cached

      # Failures are the interesting case, so the run must continue to the
      # publishing steps. The job is failed again at the very end.
      - name: Run tests
        id: tests
        continue-on-error: true
        run: |
          pytest -m "$SUITE" \
            --html=report/index.html --self-contained-html \
            --css=config/report/report.css \
            --alluredir=allure-results

      - name: Label this run
        id: meta
        run: |
          echo "label=$(date -u +%Y-%m-%d_%H-%M)-run${{ github.run_number }}" >> "$GITHUB_OUTPUT"
          echo "status=${{ steps.tests.outcome }}" >> "$GITHUB_OUTPUT"

      - name: Upload traces and screenshots
        if: steps.tests.outcome == 'failure'
        uses: actions/upload-artifact@v4
        with:
          name: test-results-${{ steps.meta.outputs.label }}
          path: test-results/
          retention-days: 14

      # The repo is already checked out, so a worktree is cheaper than a
      # second clone. Create the branch as an orphan on the very first run.
      - name: Prepare the Pages worktree
        run: |
          git fetch origin gh-pages || true
          if git show-ref -q refs/remotes/origin/gh-pages; then
            git worktree add gh-pages origin/gh-pages
          else
            git worktree add --detach gh-pages
            git -C gh-pages checkout --orphan gh-pages
            git -C gh-pages rm -rf . > /dev/null 2>&1 || true
          fi

      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "17"

      - name: Generate the Allure report
        run: |
          curl -sL https://github.com/allure-framework/allure2/releases/download/2.29.0/allure-2.29.0.tgz \
            | tar -xz -C /opt
          # Trends only exist if the previous report's history is carried over.
          prev=$(ls -1d gh-pages/allure/"$SUITE"/*/ 2>/dev/null | sort | tail -1)
          [ -n "$prev" ] && cp -r "$prev/history" allure-results/ || true
          /opt/allure-2.29.0/bin/allure generate allure-results --clean -o allure-report

      - name: Publish and rebuild the index
        run: |
          label='${{ steps.meta.outputs.label }}'
          status='${{ steps.meta.outputs.status }}'

          for pair in "report:reports" "allure-report:allure"; do
            dest="gh-pages/${pair##*:}/$SUITE/$label"
            mkdir -p "$dest"
            cp -r "${pair%%:*}/." "$dest/"
            echo "$status" > "$dest/status.txt"
          done

          # Keep the 20 newest runs per format and suite; labels sort by date.
          for dir in gh-pages/reports/*/ gh-pages/allure/*/; do
            [ -d "$dir" ] || continue
            ls -1 "$dir" | sort -r | tail -n +21 | while read -r old; do
              rm -rf "${dir}${old}"
            done
          done

          python config/report/build_index.py --pages-dir gh-pages
          touch gh-pages/.nojekyll        # keep Jekyll away from the assets

          cd gh-pages
          git add -A
          git -c user.name='github-actions[bot]' \
              -c user.email='41898282+github-actions[bot]@users.noreply.github.com' \
              commit -m "$SUITE $label ($status)" || exit 0
          git push origin HEAD:gh-pages

      - name: Reflect the test outcome
        if: steps.tests.outcome == 'failure'
        run: exit 1
```

A few choices worth calling out, since they are the parts that usually break:

- **`continue-on-error` on the test step, not the job.** A red run is exactly
  the one whose report you want published; the last step re-fails the job so
  the commit status and the badge still tell the truth.
- **`.nojekyll`.** Without it Pages runs Jekyll, which silently drops the
  underscore-prefixed files Allure generates.
- **A serialised `concurrency` group.** Two runs pushing to `gh-pages` at the
  same time is the classic non-fast-forward failure. Queuing costs a minute;
  `cancel-in-progress: true` would throw away finished reports.
- **Allure history is copied in from the previous run.** Trends are a property
  of the report directory, not of the results — skip this and every report
  looks like the first one ever generated.

## A note on the target environment

`opensource-demo.orangehrmlive.com` is a **public, shared** instance. Anyone
can be logged in and editing records while the suite runs, which shapes a few
rules in this repo:

- **Generate every value.** Faker factories in `src/data` keep runs from
  colliding with each other and with strangers.
- **Assert on what you created,** never on global counters or "the first row
  in the table" — both change under you mid-run.
- **Clean up through the API layer,** and treat cleanup as best-effort: the
  data may already be gone.
- **Never run destructive scenarios** against admin-level shared records.
- The instance is also **reset periodically** and occasionally slow. A rare
  red nightly is worth checking against the report before assuming a
  regression in the framework.
